# TurboMojo

A text-mode IDE for [Mojo](https://www.modular.com/mojo), written entirely in Mojo and modelled on
Borland Turbo C++ 3.0 (1992). It has the blue desktop, double-line windows, drop shadows,
menus with highlighted hotkeys and the "Compiling… Press any key" box. Under that look it is
a full IDE: the Mojo language server (problems as you type, completion, hover, go to
definition, references, rename, quick fixes), build and run, a debugger, integrated
terminals and the REPL, a test explorer, git, coding agents (ACP), plugins, help that
explains Mojo's error messages, and a fuzzy command palette - in a program that starts in
about 50 ms and uses about 12 MB of memory.

## Build & run

```bash
pixi run build                         # -> build/tmide
pixi run ./build/tmide examples/hello.mojo
```

Requirements: Linux with glibc 2.34 or newer. pixi fetches everything else: the Mojo toolchain and, from conda-forge, `libghostty-vt` (Ghostty's terminal emulator core, MIT licence), which the build links in statically for the integrated terminal - the built program does not need it at run time. macOS: the system-dependent parts are selected at compile time (`src/platform.mojo`) and the whole IDE compiles for `arm64-apple-macosx`, but it has never been linked or run on a Mac, and the project's pixi environments are Linux only, so macOS is not supported yet.

`pixi run` puts the Mojo toolchain on `PATH`. The IDE also works when started directly, as long
as `mojo` is on `PATH`: it then works out the toolchain's environment (`MODULAR_HOME`) itself.
To use a different compiler binary, set `TURBOMOJO_COMPILER` or change it under
**Compile ▸ Compiler command…**.

It works best in a terminal with 24-bit colour and SGR mouse support (kitty, WezTerm, iTerm2,
GNOME Terminal, Windows Terminal and others). Colour depth is taken from `$COLORTERM` and
`$TERM`, and the IDE falls back to 256 or 16 colours where needed; set
`TURBOMOJO_COLORS=truecolor|256|16` to override. At start-up the IDE also asks the terminal
(DECRQSS) whether a 24-bit colour it set took, and (XTGETTCAP) whether it draws coloured,
curly underlines; a yes adds to what the environment says, a no or no answer takes nothing
away, and your override always wins. Inside tmux the answers come from tmux itself and are
believed; without one you get 256 colours unless `COLORTERM=truecolor` is passed through.
Under GNU screen these two questions are not asked (screen passes such requests on badly).
Replies that arrive late are swallowed, never typed into the editor. To see what your
terminal reports:

```bash
pixi run ./build/tmide --caps
```

## Installing

**As a conda package.** `pixi run package` builds `turbomojo` with rattler-build
(recipe: `recipe/recipe.yaml`) into `build/conda/`. Install it from there into pixi's
global tools, so `tmide` is on your `PATH`:

```bash
pixi run package
pixi global install --channel ./build/conda --channel https://conda.modular.com/max --channel conda-forge turbomojo
tmide --version
```

The package holds the program (with the terminal emulator linked in), the example plugin
and the plugin API; it depends on `mojo-compiler` of the version it was built with, for the
Mojo runtime libraries. Building it and running `tmide --version` from it in a fresh
environment are tested; `pixi global install` itself was not run here.

**From the source.** `pixi run build` makes `build/tmide`. It finds the Mojo runtime
libraries in this project's `.pixi` environment, so run it from there (`pixi run
./build/tmide`) or keep that environment.

`tmide --version` prints the version, `tmide --help` the command line.

## Configuration

Settings are read from `~/.config/turbomojo/config.toml`, then from a `.turbomojo.toml` in the
working directory or the nearest parent folder (the project file wins):

```toml
[ui]
theme = "midnight"          # classic | midnight | amber | light | contrast | okabe | muted | auto (see Themes)
keymap = "modern"           # modern | turbo (WordStar keys) | emacs
layout = "classic"          # classic (overlapping windows) | tiled (panes with tabs, splits)
restore_session = true      # started without a file: open what was open in this project last time
line_numbers = true
highlight_line = true
clock = true
run_in_terminal = true           # Run in the Run window; false: on the user screen, as before
show_whitespace = false

[editor]
auto_indent = true
soft_wrap = false           # continue long lines on the next screen row (Alt-Z)
semantic_colors = true      # colours from the language server over the built-in ones
quiet_colors = false        # four code colours; errors and search hits stand out most
inlay_hints = true          # the language server's notes (inferred types) after the line
persistent_undo = true      # keep undo history, cursor, scroll and folds between sessions
auto_pairs = true           # typing ( [ { " ' also inserts the closing one
highlight_word = true       # show the other uses of the word the cursor is on
trim_trailing_whitespace = false   # on save (.editorconfig overrides)
rulers = []                 # e.g. [80, 100]: vertical guides after these columns

tab_width = 4               # display width of a tab character
indent_size = 4             # spaces per indent level
large_file_mb = 50          # files above this size open in large-file mode

[tools]
compiler = "mojo"           # the TURBOMOJO_COMPILER environment variable overrides this
lsp_server = "mojo-lsp-server"   # TURBOMOJO_LSP overrides this
debug_adapter = "mojo-lldb-dap"  # TURBOMOJO_DAP overrides this
include_paths = []          # extra -I folders for build, run and the language server;
                            # relative ones start at the folder of the config file
docs_paths = []             # folders of library sources whose documentation Ctrl-F1 should find
docs_home = ""              # where the downloaded Mojo documentation is kept (empty: ~/.local/share/turbomojo/docs)

[keys]                      # command name = one key or a list of keys
"file.save" = ["F2", "Ctrl-S"]
"edit.duplicateLine" = "Alt-D"
"search.gotoLine" = "Ctrl-Q L"       # two keys in a row: press Ctrl-Q, then L
```

Changing something in the Options menu writes just that setting back to your user file and
leaves the rest of the file, including comments, alone. Command names for `[keys]` are listed in
`src/commands.mojo` (`file.open`, `compile.build`, `search.find`, ...). Mistakes in a config file
are shown in the status line at startup and written to the log; the IDE still starts.

**EditorConfig.** A `.editorconfig` in the file's folder or above it is honoured per file:
`indent_style`, `indent_size`, `tab_width`, `end_of_line` (lf/crlf), `insert_final_newline` and
`trim_trailing_whitespace`. These override the `[editor]` sizes above and the tab/space
auto-detection. The status bar shows the result, for example `LF  Spaces:2`.

## Features

| Area | What you get |
|---|---|
| Desktop | Overlapping windows with drag-to-move (title bar), drag-to-resize (bottom-right corner), zoom in three steps (F5: half the desk - the half the window is mostly in - then the whole desk, then back; in the tiled layout half gives the pane at least half the width and height with the other panes still in view, and is passed over where it would change nothing), tile/cascade, Alt-1…9 window numbers, a window list (Alt-0), **F6** to the window used last (pressed again in a row: further back, as Alt-Tab does; Shift-F6 back along that, or on its own the window used least lately) and drop shadows |
| Editor | Mojo syntax colouring (keywords, types, builtins, strings and docstrings, numbers, decorators, def names), line numbers, current-line highlight, bracket matching, smart Home, auto-indent (indents after `:`), Tab/Shift-Tab block indent, toggle comment, duplicate/delete line, insert/overwrite modes (underline or block cursor) |
| Undo | Grouped undo/redo. Typing a word undoes as one step, and so does Replace-all or Format |
| Soft wrap | Options ▸ Soft wrap (Alt-Z): long lines continue on the next screen row, broken after a blank where possible. Up/Down move by screen rows, the view scrolls inside a line taller than the window, and line numbers mark only the first row of each line |
| Folding | Blocks are found by indentation. Alt-- (Edit ▸ Fold or unfold) hides or shows the block at the cursor, from its header or from any line inside it; clicking the ▾/▸ marker in the line-number gutter does the same. Fold all, and Expand all (Alt-=). A folded header shows how many lines it hides; moving the cursor skips them, and jumping into one (search, go to line, an error) opens it |
| Text menu | Move line up/down (Alt-Up/Down, also for selected lines), Join lines (Alt-J), Sort lines, Upper/Lower case (Alt-U / Alt-L) for the selection or the word at the cursor |
| Typing aids | Auto-closing pairs: `(`, `[`, `{` and quotes insert their partner, typing the closer steps over it, Backspace removes an empty pair, and with a selection the pair wraps it. Column rulers (`editor.rulers`). Trailing whitespace can be trimmed on save |
| Keymaps | Options ▸ Keys: **Modern** (default), **Turbo / WordStar** (the Ctrl-E/S/D/X cursor diamond, Ctrl-Y, Ctrl-T, and Ctrl-K / Ctrl-Q sequences such as Ctrl-K S save, Ctrl-Q F find, Ctrl-Q R top of file) or **Emacs** (Ctrl-A/E/F/B/N/P, Ctrl-K, Ctrl-Y, Ctrl-X Ctrl-S, Ctrl-X Ctrl-C...). Function keys work the same in all three. Any command can be bound to one key or to a two-key sequence in `[keys]`; menus show the active keys |
| Keyboard | On terminals that support the kitty keyboard protocol (kitty, Ghostty, WezTerm, foot, recent Alacritty...) the IDE switches it on, so Esc is instant and unambiguous and combinations such as Ctrl-Shift-P, Ctrl-I (distinct from Tab) or Ctrl-Backspace (delete word left) can be told apart and bound in `[keys]`. Other terminals work as before |
| Macros | Ctrl-F5 starts and stops recording ("● REC" shows in the status line), Ctrl-F6 replays. Keys, pastes and commands picked from menus are recorded, including dialogs such as Replace, so a macro can be played on line after line or at several cursors |
| Encodings | UTF-8, with a byte order mark kept if the file has one. A file that is not valid UTF-8 is read as Latin-1 (one character per byte) and saved back byte for byte; the status line shows "Latin-1" or "UTF-8 BOM". A file with both LF and CRLF line ends shows "Mixed>LF" (or "Mixed>CRLF") until it is saved with the kind shown |
| Between sessions | Reopening a file - after closing it, or in a later run - puts the cursor and the scroll where they were, folds the blocks that were folded and brings back its undo and redo history, as long as the file still has exactly the content it had when the history was saved. Kept under `~/.local/state/turbomojo/history` (the 500 most recent files); `editor.persistent_undo = false` turns it off |
| Problems (language server) | F7 starts the Mojo language server. Problems are underlined where they are (curly and coloured on terminals that can; plain otherwise, `TURBOMOJO_UNDERLINE=curly` or `plain` decides), the line number takes the colour of the worst problem on its line, and the status line shows the message for the cursor line. The **Problems** window lists them for all open files; Enter jumps, Alt-F8 / Alt-F7 go to the next and previous one |
| Completion | Ctrl-Space shows words from the file at once; with the language server running (F7) its suggestions are merged in on top, with a tag for the kind (`fn`, `var`, `typ`...), the signature or type beside the name, and a panel with the documentation of the selected item. Typing `.` asks the server for members by itself. Typing narrows the list, Enter or Tab accepts |
| Describe symbol | Alt-I (Search ▸ Describe symbol) asks the language server about the symbol at the cursor and shows the answer in a window under it: signature in the editor's syntax colours, documentation with headings, lists, **bold**, `code` and links rendered from Markdown. Arrow keys and PgUp/PgDn scroll; Esc closes; any other key closes it and does what it normally does |
| Parameter tip | Typing `(` or `,` in a call (the characters the language server names) shows the signature of the function on the row above the cursor, with the parameter being typed highlighted and underlined; it follows the cursor through the arguments and disappears when the call is closed or left. Several signatures show as "2/3"; parameter documentation appears below; a signature wider than the screen is shown around the current parameter. Alt-P (Search ▸ Parameter info) asks for it anywhere; Esc hides it |
| Go to definition | F12 (Search ▸ Go to definition) asks the language server where the symbol at the cursor is defined and goes there, opening the file if needed. Several definitions are listed in the Message window (Alt-F8 / Alt-F7 step through them) |
| Find references | Shift-F12 (Search ▸ Find references) lists every use of the symbol at the cursor, its definition included, in the Message window as file:line:column with the line's text - the file being edited first, other files after it. Enter on a line, or Alt-F8 / Alt-F7, goes to a use; Alt-, comes back |
| Rename symbol | Shift-F2 (Search ▸ Rename symbol) asks for a new name and has the language server rename the symbol everywhere. Every change is listed in the Message window. Changes in this file only are applied at once and one Undo takes them back; when other files are affected the IDE asks first, then opens them and changes each in one undo step - nothing is saved until you save. Note: the Mojo 1.2 server renames local variables only and says so for anything else |
| Quick fix | Alt-Enter (Search ▸ Quick fix) asks the language server what it can do about the problems on the cursor's line or the selection, and lists the offers - the server's preferred fix first; ones that cannot be used say why. Enter applies the chosen one as one undo step; changes reaching other files are listed and confirmed first, as with Rename. Note: the Mojo 1.2 server answers but offered no fixes for the errors tried |
| Semantic colours | With the language server running, names are coloured by what they are - functions and methods at their calls, types, fields, parameters, namespaces - on top of the built-in highlighter, which keeps colouring keywords, strings, comments and numbers. The colours move with the text while you type and are refreshed after each edit. Options ▸ Semantic colours (`editor.semantic_colors`) turns them off |
| Quiet code colours | Options ▸ Quiet code colours (`quiet_colors = true` under `[editor]`) folds the theme's code colours into four, as restrained schemes do: text (keywords, types and the rest too), comments, strings and numbers, and definitions. Strings and definitions become the calmest colours near their own that are clearly quieter than the error colour, so problems, search hits and the current line stand out most - checked in the tests for every theme and colour depth, with the same contrast floors and colour-vision check as the theme's own colours. Off by default; any theme |
| Inlay hints | Notes from the language server (inferred types, parameter names) are shown dimmed after the end of the line as `◂ total: Int`; they are not part of the text. Options ▸ Inlay hints (`editor.inlay_hints`). Note: the Mojo 1.2 server sent no hints for the code tried |
| Outline | Ctrl-F12 (Window ▸ Outline) shows the file's structure in a window at the right edge: structs, traits, functions and methods as an indented tree, plus fields and variables when the language server is running. It follows the editor in front, updates as you type, and marks the symbol the cursor is in. Switch to it (F6) and press Enter, or click a line twice, to go to that symbol; Ctrl-F12 again closes it. Without a server a built-in scan of the text is used |
| Other uses of a word | With the cursor on a name, every other whole-word use of it on screen gets a quiet background - no language server needed. Off while a search's matches are shown or text is selected; `editor.highlight_word = false` turns it off |
| Go to symbol in project | Alt-F12 (Search ▸ Go to symbol in project) lists every def, struct, trait and constant of the project's Mojo files; type a few letters of a name (or of the struct it belongs to) to narrow the list, Enter goes there. The index is built in the background (hidden folders and `.gitignore`d ones are skipped), includes unsaved changes of open files, and is refreshed on save and when it is older than 20 seconds |
| Documentation (Topic search) | Ctrl-F1 (Help ▸ Topic search) shows the documentation of the name at the cursor in a window: signature, summary, arguments, result, and for a struct its fields and methods - taken from the docstrings with `mojo doc`, no language server needed. F1 does the same when the cursor is on a name it has documentation for, and shows the keyboard reference otherwise. Covers the project's Mojo files and the folders in `tools.docs_paths`; the installed standard library ships without sources, so for its names Ctrl-F1 falls back to the language server's description when the server is running |
| Tiled layout | Window ▸ Tiled layout (or `layout = "tiled"` under `[ui]`) replaces the overlapping windows by panes that share the screen. Every open file is a tab of a pane; the tabs stand in the pane's top border and can be clicked. Alt-\\ moves the file in front into a new pane to the right, Alt-\| into one below; Alt-F6 goes to the next pane, Alt-PgDn / Alt-PgUp to the next / previous tab; Window ▸ Move to next pane, Grow pane (Alt-}), Shrink pane (Alt-{). Closing the last file of a pane gives its room back; Zoom (F5) lets one pane take everything. The Message and Outline windows keep the bottom and the right edge. The classic layout stays the default |
| Bottom panel | The window at the bottom has three pages, shown as tabs in its top border: **Message** (compiler and program output), **Search** (Find in Files results, references and other lists of places) and **Problems** (what the language server reports for all files, the last build's errors and warnings, and the tests that failed, marked `[build]` and `[test]`; the current file first). On the Problems page **E**, **W**, **N** show or hide errors, warnings and notes, **F** shows only the current file's, **/** asks for a text the rows must contain and **C** shows everything again; the second line says what is shown and the last how many are hidden. Its tab counts them, `Problems (3 E, 7 W)`, with `; 4 shown` while the filter hides some (the counts give way in a narrow panel). On the Message page **/** shows only the output lines containing a text (Enter still jumps from them) and **C** shows all; new output comes unfiltered. Each page keeps its own content and its own list for Enter and Alt-F8 / Alt-F7. Window ▸ Message / Search results / Problems list opens a page; with the panel focused, Left / Right (or Alt-PgUp / Alt-PgDn, or a click on a tab) switch pages and Alt-} / Alt-{ make it higher or lower (the Outline window: wider or narrower). New problems come to the front only if you have not turned to another page |
| File explorer | Ctrl-E (Window ▸ File explorer) opens the project's files as a tree at the left edge; editors move over, and the file being edited is marked. Only folders you open are read. In it: Enter opens a file or opens / closes a folder, Right / Left step into and out of folders, **N** new file, **F** new folder, **R** rename, **M** move to another folder of the project, **Del** move to the trash (after a question; nothing is deleted outright - it goes to the desktop's trash folder and can be restored from there), **.** shows files that `.gitignore` hides, **U** reads the folders again (it also happens by itself every two seconds), **/** shows only the names that contain some text (any case) with the folders above them - the title then says how many rows are shown of how many, `2/9 /test` - and **C** shows all again. Open windows follow a renamed or moved file. Esc returns to the editor; Ctrl-E from inside closes the explorer |
| Palette ("Go to") | One field for going anywhere. Alt-G (File ▸ Go to file) lists the project's files - the ones you open often and lately first - and narrows as you type a name or folder; `name:12` or `name:12:5` opens at that line (and column). Start with `>` for commands (Ctrl-P opens it that way), `@` for the symbols of the file in front, `#` for symbols of the whole project, `:` for a line of the file in front. The title says how many entries what you typed leaves of how many, `Go to  12/340`. Enter goes there, Esc leaves; Alt-, comes back |
| Git markers | In a git repository, the line-number gutter gets a column that shows how the text differs from the file's version in git's index (what `git add` last took): **+** added lines, **~** changed lines, **‾** lines removed above this one, **_** removed at the end. It follows your edits as you type, before saving. The file explorer shows each file's `git status` after its name - **M** modified, **A** added, **R** renamed, **D** deleted, **U** untracked, **C** conflict - in colour, a **•** on folders with changes in them, and the branch in its title. A commit, `git add` or checkout made elsewhere (a terminal) shows within a couple of seconds. git can run commands a repository's own configuration names, so all this only happens in folders you have trusted (see Folder trust); nothing asks for it |
| Git changes | File ▸ Diff of this file shows the file's changes against git's index as a unified diff (+ green, - red), as you have edited it, saved or not. In it: **S** stages the change under the cursor (only that block goes into the index - the file on disk is not touched), **R** reverts it in the editor (an ordinary edit: Undo brings it back), **Enter** goes to the line, **Tab** switches to what is staged (the index against the last commit), where **U** unstages a change (a new file whose only change is unstaged leaves the index), **Esc** closes. From the editor: File ▸ Stage change and Revert change work on the block at the cursor, Alt-N / Alt-B (File ▸ Next / Previous change) move between changed blocks |
| Git commit, branches, blame | File ▸ Commit opens a dialog with the staged files, a summary and details, **Amend the last commit** (with no summary it keeps the message) and **Include all changes to tracked files** (ticked when nothing is staged). git's hooks run; if git refuses, its own message is shown. File ▸ Branch lists the branches (the latest first, * the current one): type to filter, Enter switches, **New branch** (or Enter on a name no branch has) makes one here; files git changes on disk are reloaded. File ▸ Blame shows who last changed each line of the file as edited, when and in which commit (`(not committed)` for your own new lines); the status line shows the commit's summary, Enter goes to the line |
| Coding agent | File ▸ Agent panel (Ctrl-F11) talks to a coding agent that speaks the Agent Client Protocol, named by `agent = "..."` under `[tools]` (or `TURBOMOJO_AGENT`), for example `claude-agent-acp`, `gemini --experimental-acp` or `codex-acp` - installed and signed in once in a terminal. It runs in the project folder (so it needs folder trust) and opens at the right edge: the conversation as Markdown, growing while the agent answers, with its thinking, the tools it uses and its plan; the prompt on the last lines. Enter sends; Esc stops a turn that runs, else returns to the editor; Up / PgUp scroll back. `@path` or `@path:12-20` in a prompt sends that file or those lines along, from the editor when it is open there (unsaved changes count); Shift-F11 puts the editor's selection (or file) in. Ctrl-F11 from the panel closes it; the session goes on. The agent reads files through the editor (your unsaved text, files of the project or open in the editor). A change it sends through the editor never goes in by itself: it shows in the diff view as **Proposed: name** - **A** accepts it (put into the editor as one Undo step and saved), **R** rejects it (the agent is told), Esc leaves it waiting (Enter in the empty prompt shows it again). A command it wants to run is asked in the panel and runs on a terminal of its own; its last lines show in the conversation. Agents with tools of their own (Claude Code's adapter, `claude-agent-acp`, edits files itself) are put into the mode in which they ask before changing anything (`agent_mode = "ask"` under `[tools]`, the default; `""` keeps the agent's own mode, or name one of its modes) - then they ask permission for each edit and command. **Permissions**: every request is asked in the panel - **Y** allows it once, **A** for the rest of the session (a command exactly as written; anything else by its kind, e.g. every edit), **N** refuses; Esc stops the turn and cancels what it asked. The commands TurboMojo runs for the agent ask the same way (Y, A, N), and **S** in a proposal's diff view accepts it and the session's later writes. What was allowed ends with the agent's session. Nothing is allowed until you say so, and the agent stops when the folder's trust is taken back |
| Notifications | When something finishes or needs you while you are elsewhere - a build (succeeded, with warnings, failed), a test run, a pixi task, a git commit or branch switch, the agent finishing or asking for permission, the language server failing - a short notice shows at the top right for a few seconds (failures for ten); a click takes it away. The status line shows ⟳ and how many things are running in the background. Help ▸ Notifications (Shift-F10) lists what is running now (build, git, agent and its commands, symbol index, search, the program) and the notices of this session, newest first; Clear all empties it. Toasts do not interrupt typing: one that comes while the editor has the keys waits until a pause (2.5 s without a key), a save or the debugger stopping. A job you started yourself (a build, tests, a task, a commit, a branch switch) is shown at once, first, and brings the waiting ones with it. Nothing in the background takes the keyboard: the agent asking for permission or to run a command, or proposing a change, brings its panel or the diff view to the front only when you are in the agent panel and not typing - otherwise a notice says the key (Ctrl-F11) - and a panel a plugin opens by itself stays beside your window. The build's Compiling box and the jump to the Message window come only if you waited for the build; if you went on typing, the notice is enough. A debugger that fails to start is a notice too; boxes are kept for questions |
| Help | Help ▸ Keyboard reference (F1) lists every key as your keymap has it. Help ▸ TurboMojo guide, Cheat sheet and What's new open TurboMojo's own book in the documentation viewer (above the Mojo documentation, which need not be downloaded for it); **/** there searches it together with the Mojo documentation, and its Keyboard reference page shows your keys. Help ▸ Tutorial opens your own copy of a practice file - lessons on moving, selecting, the palette, finding, running and debugging, with a small program to try them on; it is kept while open, and a fresh copy comes once it is closed. After an upgrade a notice says what is new, once. The pages are the files in `help/` |
| Links | Every `file:line` the Message window shows (build errors, search hits, problems) and every reference to an existing file in the agent panel is a terminal hyperlink (OSC 8): with mouse reporting on, follow it with your terminal's modifier - Ctrl-Shift-click in kitty, Shift-click (or Ctrl/Cmd-click) in most others. `hyperlink_format` under `[ui]` says where it goes, like ripgrep's `--hyperlink-format`: `{host}`, `{path}`, `{line}`, `{column}`; the default `file://{host}{path}` opens the file with the system's handler, `"vscode://file{path}:{line}:{column}"` opens it in VS Code at the line. `hyperlinks = false` sends none (a terminal without OSC 8 ignores them anyway) |
| Glyphs | `glyphs` under `[ui]` picks the characters the IDE draws its own frames, menus and marks with. `unicode` (the default) is the Turbo look: box drawing, shading, arrows, ✓ ✗ - all one cell wide, no emoji. `ascii` sends nothing but ASCII (`+`, `-`, `=`, `|`, `^ v < >`, `#`, `.`), for a font or terminal without those characters, or a CJK terminal that draws box drawing two cells wide; symbols in your files are shown the same way while the files stay as they are. `nerd` adds Nerd Font icons before files and folders in the explorer and before notifications - only for a terminal whose font is a Nerd Font |

On the very first run (no config file yet, started without file names) TurboMojo opens that box by itself, once, with a welcome line; `NO_COLOR` skips it. **Terminal ANSI** (`ansi`) uses only your terminal's own 16 colours and its default foreground and background, so the terminal's colour scheme and its contrast settings decide how TurboMojo looks; **Terminal Mono** (`mono`) uses the default colours only, with black on white for the selection and the menu bar, and is what TurboMojo starts with when `NO_COLOR` is set (https://no-color.org) and the config file names no theme. In theme files a colour can be `ansi:0` to `ansi:15`, `256:0` to `256:255` (the xterm-256 colours) or `default`. A theme can set colours by the part they play in `[roles]` - `surface` (editor and list backgrounds), `panel` (dialogs, menu bar, status line), `text`, `text_muted`, `text_disabled`, `border`, `border_blurred`, `cursor` (the highlighted row of menus and lists), `diag_error`, `diag_warn` - each standing for all the colours of that part, and can be designed for terminals with fewer colours: `[colors256]` / `[syntax256]` and `[colors16]` / `[syntax16]` are used there instead of the nearest colours. Every built-in theme has them where the nearest colours would fall short: as a 256-colour terminal shows it, each theme reaches the same contrast floors as in truecolor; with 16 colours (measured with the VGA values, as terminals differ) WCAG 4.5:1 for text and never text in its background's colour. So in 16 colours Turbo Classic's hot letters are blue rather than red (red on grey is 3.3:1), and Amber CRT is yellow on black. `theme = "auto"` follows the terminal's light or dark setting (mode 2031: Ghostty, kitty, recent foot and others report it, also when it changes), using `theme_dark` and `theme_light`. A terminal that does not report it but answers what its background colour is (OSC 11) is judged by that colour's lightness, and asked again when it gets the focus back and at most every half minute while you work, so a change of its colours is followed too; one that does neither (GNOME Terminal) is followed through the desktop: `COLORFGBG` if the terminal sets it, else GNOME's dark / light setting, looked at again every half minute; with neither, the dark one. Your own themes are TOML files in `~/.config/turbomojo/themes/` - `name`, `dark`, an optional `base` theme to start from, `[colors]` (any colour of the palette by name, `"#RRGGBB"`) and `[syntax]` (text, keyword, type, comment, string, number, decorator, symbol, builtin, self, def, param, property, namespace); the shipped ones in `themes/` are examples. A theme can set `scanlines = true`: every other row a little darker, a CRT look; `scanlines = false` (or `true`) under `[ui]` overrides every theme - e.g. off when the terminal draws its own CRT effect (Ghostty's `custom-shader`). Mistakes in a theme file are listed with the other configuration warnings. Every built-in theme is measured in the tests (`src/contrast.mojo`): text, code and selections at least WCAG 4.5:1 and APCA Lc 45, comments, line numbers and dim text 3:1 and Lc 30, disabled items Lc 15, and High Contrast's text 7:1 and Lc 60. Every theme is also checked through simulated protanopia, deuteranopia and tritanopia (Machado et al. 2009): the problem severities, success and failure and the git markers stay at least 20 apart (CIE delta E), and main syntax classes that differ stay 10 apart (a theme may give two the same colour on purpose). Amber CRT and Terminal Mono are of one hue by design (`monochrome = true` in a theme file) and tell these apart by the letters E W i and the git marks + ~ ‾ _ alone - as every theme does too, besides the colours |
| Robustness | **Unsaved work survives crashes:** every modified buffer is copied to a swap file 2 seconds after a change, and after a crash, `kill -9` or power loss the next start offers to recover it (Recover / Discard / Later). Being killed politely (`kill`, closing the terminal, logging out) keeps the buffers the same way and restores the terminal. Your own files are never written without a save. **Files changed by other programs** are noticed at once: an unmodified buffer reloads quietly (undoable), and if you have unsaved changes you are asked whether to reload or keep your version. Resizing is picked up instantly; `kill -TSTP` / `fg` suspends and resumes cleanly. If the IDE itself crashes, the terminal is restored and a stack trace goes to `~/.local/state/turbomojo/crash.log`. An idle IDE uses no CPU |
| Rendering | Double-buffered diff renderer with 24-bit colour and synchronized output (no tearing). A frame sends only the cells that changed, and nothing at all when none did; the cursor is hidden, shown or reshaped only when that changes. After every frame the terminal's cursor is on the editor's caret (or a terminal program's own cursor); with no caret - a list window, an open menu, a dialog's button - it waits hidden on the focused row or item, so screen magnifiers that follow it find the focus and a toast, the clock or the spinner never leaves it elsewhere |

Press **F1** inside the IDE for the keyboard reference of your keymap; [docs/KEYMAP.md](docs/KEYMAP.md) has all three keymaps. The [user guide](docs/USER_GUIDE.md) walks through the IDE.

## Source layout

All Mojo, over 40,000 lines in more than a hundred modules; the only library linked in is
libghostty-vt, the terminal emulator of the integrated terminal. The screen (`screen.mojo`)
and the terminal's input (`term.mojo`) at the bottom; the text (`rope.mojo`, `buffer.mojo`)
and its windows (`window*.mojo`); the protocols, each a client of its own - language servers
(`lsp.mojo`), the debugger (`dap.mojo`), coding agents (`acp.mojo`), plugins (`plugins.mojo`)
over one JSON-RPC layer (`rpc.mojo`); and the application, the `App` struct of
`appstate.mojo` extended area by area by the `app_*.mojo` files. System differences are in
`platform.mojo`. [docs/SOURCE.md](docs/SOURCE.md) lists every file.

## Testing

```bash
pixi run check
```

builds the IDE, compiles and runs every `tests/test_*.mojo` (std.testing TestSuite files), and
runs a scripted smoke test of the real UI in a private tmux server. It prints `CHECK OK` only
if everything passed. To build one test by hand: `pixi run mojo build -I src tests/test_vt.mojo -o build/tests/test_vt -Xlinker .pixi/envs/default/lib/libghostty-vt.a`.

The project builds against the stable Mojo release (1.2 or newer). A second environment tracks
the nightly toolchain as an early warning for upcoming changes:

```bash
pixi run canary
```

`scripts/fuzz.sh [rounds] [iterations]` fuzzes the key parser, the JSON parser, the rope and
the terminal emulator with new random seeds (tests/test_fuzz.mojo, which the gate runs
briefly with a fixed seed). Each checks a property - the same key events however the
input is split, JSON that survives a round trip, a buffer that agrees with a simple model
and undoes back to its start, a terminal screen that keeps its size and cursor - and a
failure prints the seed that replays it.

`scripts/perf.sh` checks the performance budgets, and `pixi run check` runs it at the end
(`SKIP_PERF=1` leaves it out). Measured on the development machine (aarch64, 20 cores) and
the budget each must stay under:

| | Measured | Budget |
|---|---|---|
| Start-up, until the file is on screen | 46-49 ms | 400 ms |
| A key until it is on screen, beyond tmux's own round trip (about 4 ms) | 1-2 ms | 30 ms |
| Opening a 1,000,000-line file | 115-123 ms | 1000 ms |
| CPU while idle for 10 s | 0-10 ms | 100 ms |

Each run is added to `build/perf-history.csv`. The IDE runs with configuration and state
folders of its own there, so nothing of yours is read or changed.

`scripts/soak.sh [minutes]` edits for a long time - open a file through the palette, type,
undo, find, open menus, resize, save, close, over and over - and watches the IDE's memory;
it fails if the IDE ends, its screen breaks, the crash log gets an entry, or the memory
keeps growing. The gate runs it for a minute. A 30-minute run (750 cycles) went from 15.5 MB
to 17.2 MB while warming up and then stayed at 17.5 MB.

`scripts/bench-open.sh` generates a 1,000,000-line file and a 60 MB file under `build/big/` and
times how long the editor's loader takes to open them (it fails above 1 s for the first).

`scripts/tui-test.sh` lets you script key presses by hand and capture the screen:

```bash
scripts/tui-test.sh start examples/hello.mojo
scripts/tui-test.sh keys F9          # build
scripts/tui-test.sh shot             # print the screen
scripts/tui-test.sh stop
```

## Known limitations

- Grapheme clusters use built-in tables for common scripts and emoji, not the full Unicode database; Indic conjuncts are split after the virama. Emoji sequences line up only on terminals that report grapheme clustering (mode 2027); elsewhere their parts are laid out side by side. Dialog input fields still step by codepoint.
- Searching works line by line: a pattern cannot match across a line break, and matches of length zero are skipped. In texts over 50,000 lines the search runs when you press Enter instead of while you type, and matches are not counted.
- Only UTF-8 and Latin-1 are handled: other encodings (UTF-16, Windows-1252's extra characters, Shift-JIS...) open as Latin-1 characters. There is no command to convert a file between encodings or to add or remove the byte order mark. If you type a character Latin-1 cannot hold into a Latin-1 file, it is saved as UTF-8 and the status line says so.
- The saved undo history contains text you deleted, in plain form, in your state directory (the folder is created for your user only). It is written when you save, close an unchanged file or quit; if another program changes the file, its history is not used again.
- While the language server runs (F7), every open `.mojo` file is kept in step with it: opened, updated 0.3 s after you stop typing (only the changed ranges when the server supports that), told about saves, and closed. Problems are known only for files that are open.
- If the language server stops unexpectedly it is started again for the file it was checking, after 1, 2 and 4 seconds; after three crashes within a minute it stays off until you press F7 again. What it offers is written to the log file when it starts.
- Find in files reads files from disk (unsaved changes are not seen), lists one hit per matching line, and skips hidden files, `node_modules`, `__pycache__`, binary files, files over 5 MB and the simple entries of the folder's `.gitignore` (`name`, `name/`, `*.ext`); other `.gitignore` rules are not applied. It stops after 5,000 hits.
- With several cursors, commands other than typing, deleting, moving and the clipboard (Tab indent, comment, duplicate line, PgUp/PgDn, Find...) first go back to one cursor. Undo also returns to one cursor. Alt-click needs a terminal that passes Alt with mouse clicks to the program.
- With soft wrap, Home and End still go to the start and end of the whole line, continuation rows are not indented, and the Message window does not wrap.
- Folds are not saved with the file or in recovery files, the fold markers need the line-number gutter, and deleting a folded header line deletes only that line (the block under it becomes visible).
- Auto-closing pairs do not look at syntax: they also act inside strings and comments. Rulers are not drawn while soft wrap is on.
- Key sequences are at most two keys long. The Turbo keymap has no block markers (Ctrl-K B / Ctrl-K K): Ctrl-K C/V/Y act on the ordinary selection. In the Emacs keymap Alt-F and Alt-W keep opening the File and Window menus rather than moving by word or copying. Some key combinations never reach a terminal program (Ctrl-M, Ctrl-I, Ctrl-H are Enter, Tab and Backspace).
- A macro is kept only until the IDE exits, there is one of it, mouse actions are not recorded, and each recorded step is its own undo step.
- Ctrl-F9 runs the program in the Run window, a terminal of its own; with `run_in_terminal = false` it gets the whole terminal instead, the way Turbo's user screen did. Build, Format and tests run in the background.
